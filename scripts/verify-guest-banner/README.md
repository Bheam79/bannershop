# Guest banner smoke (BANNERSH-305)

These standalone checks do not run the project test suite or call real image providers.

- `dotnet run --project scripts/verify-guest-banner`: real controller/service with a disposable in-memory SQLite database and ephemeral protection keys. Set `GUEST_SMOKE_MYSQL` to an **empty disposable MariaDB database** to exercise production's `EnableRetryOnFailure(3)` strategy instead. Checks guest pending/ready reads, protected-cookie isolation/expiry, authenticated idempotent claiming, portrait ownership, no duplicate designs/orders, nullable guest DTO ownership, and activation/print-asset synchronization after claim. Only the generation enqueue response is stubbed.
- Export the real API response with `GUEST_SMOKE_FIXTURE=/tmp/bannersh305-fixture.json dotnet run --project scripts/verify-guest-banner` (optionally with `GUEST_SMOKE_MYSQL` too).
- Start `npm run dev -- --port 10000 --strictPort` in `frontend`, then run `GUEST_SMOKE_FIXTURE=/tmp/bannersh305-fixture.json node scripts/verify-guest-banner/browser.mjs`. Repeat with `GUEST_SMOKE_AUTH=login` for existing-account login. Requires the existing `e2e` Playwright installation. Browser uses real Vue composable/views with mocked API responses based on the exported DTO; verifies both guest alternatives, reload preserving selection, edited form/selection after auth, and pressing Continue to reach customization. Stop Vite afterwards.
- For MariaDB, create a task-owned sibling with `cb docker run mariadb:11 --name guest305verify -e MARIADB_ROOT_PASSWORD=guest305smoke -e MARIADB_DATABASE=guest305smoke`, read its IP with `cb docker exec guest305verify hostname -I`, and use `GUEST_SMOKE_MYSQL="Server=<IP>;Database=guest305smoke;User=root;Password=guest305smoke;"`. The harness seeds fixed IDs, so each run needs an empty database. Stop and remove this temporary container afterwards (`cb docker stop guest305verify && cb docker rm guest305verify`). Never point the harness at an existing project or production database.

Original browser reproduction: `phase: anon_pending`, no preview, **0 polls**, and login's registration link dropped the redirect (`/register`).

Reopened-report reproduction (2026-09-17): the real DTO returned `userId: 0`, unlike the old browser mock's `null`; clicking Alternative 2 issued an authenticated activation request and navigated to login. MariaDB claiming threw `MySqlRetryingExecutionStrategy does not support user-initiated transactions`, which SQLite alone could not expose. Both reproductions pass after aligning the DTO and wrapping the claim transaction in the execution strategy.
